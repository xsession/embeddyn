# Deepen Renode, add MuJoCo, standardize on FMI

embeddyn's biggest gaps are best closed by going deeper into tools it already uses, plus three new permissive dependencies. Wholesale engine swaps are not needed. **Renode already ships most of the missing bus and sensor layer**: CAN and SPI hooks in its External Control API, register-level I2C sensor models, RESD sensor feeds, and maintained Verilator/DPI/SystemC bridges. So the first firmware task is rebasing the custom-cores fork onto v1.17.1 and binding what is there. **ngspice 46/47 adds diode and VDMOS soft-recovery models and Verilog/VHDL mixed-signal co-simulation inside the shared library**, which covers dead-time and gate-drive work without a new engine. The three new dependencies that matter are **MuJoCo** (Apache-2.0, in-process, native full-state save/restore) as the default mechanical domain, the **FMPy + Reference-FMUs + PythonFMU3** trio (BSD-2/BSD-2/MIT) for FMI validation, checkpointing and export, and **python-can/cantools + MCAP** for bus traffic and run logs. OpenModelica belongs offline as a plant-FMU generator, not in the runtime. Several tools should be explicitly rejected for lock-step use: Wokwi, QEMU, Velxio, PyBullet, GPU engines, GeckoCIRCUITS, Julia, DCP and Ditto. One design rule ties the plan to the CodeLayer Forge merge: everything inside the lock-step stays virtual-time-stamped and deterministic, and every bridge to real time is a logged boundary adapter. That rule matches Forge's out-of-process Python plugin hosts and JSON-RPC capabilities. It also gives a natural way to keep GPL tools at arm's length.

## Renode already holds the bus, sensor and FPGA answers

The firmware domain needs no new emulator. Renode's C External Control API now covers more than connecting: `run_for`, quantum setting, virtual time, ADC and GPIO get/set with callbacks, **CAN send/receive with 64-byte payloads**, an `ExternalControlSPIPeripheral` with MOSI/MISO callbacks, and an `ExternalControlBusPeripheral` that gets sysbus access callbacks ([Renode External Control docs](https://renode.readthedocs.io/en/latest/api-description/external-control.html)). It defines the timing exactly. `run_for` ends at a sync point. GPIO input changes land at the next sync point. CAN frames arrive at the next sync point in the default SynchronizedIO mode. ADC writes take effect before `set` returns. Nanosecond precision holds for about 93 days of virtual time (same source). embeddyn can schedule against these guarantees. Renode's test suite lists ready-made I2C/SPI sensor models: the LSM6DSO, LSM9DS1 and LIS2DW12 IMUs, IIS2MDC and AK09918 magnetometers, BME280 and LPS25HB pressure sensors, the **INA228 current monitor**, MCAN and FlexCAN controllers, and STM32 UARTs ([Renode tests/peripherals](https://opensecura.googlesource.com/3p/renode/renode/+/refs/heads/master/tests/peripherals)). The binary RESD format feeds several typed channels into these models from one file ([Renode RESD docs](https://renode.readthedocs.io/en/latest/basic/resd.html)). embeddyn can therefore push physics-derived acceleration, temperature and current into realistic register-level sensors at every step without writing sensor models.

The release history makes a rebase worth the cost. v1.17.1 shipped on 2026-11-23. It adds "extensive support for the STM32H7 Renode Reference Platform", Ethos-U NPUs, Xtensa LX7 decoding as groundwork for ESP32-S2/S3, and turns fetches from unmapped memory into a BusFault instead of halting the CPU ([v1.17.1 notes](https://github.com/renode/renode/releases/tag/v1.17.1)). v1.17.0 added precise BusFaults and Lockup handling ([v1.17.0 notes](https://github.com/renode/renode/releases/tag/v1.17.0)), which matters for fault-injection scenarios. The STM32H7 reference board is a ready-made "digital twin" target. It has six `st,stm32-qdec` quadrature decoders, two FDCAN controllers, an on-board IMU, a magnetometer, pressure, temperature and light sensors, and a potentiometer on ADC1 ([Zephyr board docs](https://docs.zephyrproject.org/latest/boards/antmicro/stm32h7_renode_reference_board/doc/index.html)). One real gap remains: **no quadrature-encoder stimulus model was found**. Toggling A/B over GPIO at 1 ms sync points caps the edge rate near 1 kHz, which is too slow for real encoders. embeddyn needs a small C# or Python Renode peripheral that turns commanded position into counter updates inside virtual time. UART and I2C have no dedicated external-control hooks. UART is still easy, because `CreateServerSocketTerminal` and `CreateUartPtyTerminal` expose it as a TCP port or pty ([Renode UART integration](https://renode.readthedocs.io/en/latest/host-integration/uart.html)). A TCP port with the telnet negotiation bytes turned off is ready to proxy to an xterm.js terminal in the Lab GUI.

For digital hardware, Renode offers two maintained HDL routes. The first is a Verilator-only C++ route: the RTL is compiled to a shared library that Renode loads, with APB3, AXI4, AXI4-Lite, Wishbone and CFU buses. The second is DPI over sockets for Verilator, Questa or VCS, with AHB, APB3 and AXI4 ([Renode HDL co-simulation docs](https://renode.readthedocs.io/en/latest/advanced/co-simulating-with-an-hdl-simulator.html)). There is also a TCP bridge to SystemC TLM sockets ([Antmicro SystemC blog](https://antmicro.com/blog/2024/07/systemc-co-simulation-in-renode/)). Bus-attached FPGA logic inherits Renode's virtual time for free, so that is the path for anything the MCU sees as a memory-mapped peripheral. Standalone logic, such as a motor-control FPGA that sits between the MCU and the power stage, fits better as its own embeddyn component. In that case embeddyn would drive a Verilator model (actively maintained, v5.054 ([Verilator](https://github.com/verilator/verilator))) by calling `eval()` with sub-steps inside each 1 ms macro step. cocotb (BSD-3, v2.1.0 ([cocotb](https://github.com/cocotb/cocotb))) is the right Python testbench layer over Verilator, Icarus or GHDL. Its control flow is inverted relative to embeddyn's orchestrator, though, so it belongs in tests rather than in the lock-step loop.

The alternatives lose on time control. QEMU is deterministic only under `-icount` with `sleep=off`, and it has no client library comparable to `run_for` ([QEMU TCG icount](https://www.qemu.org/docs/master/devel/tcg-icount.html)). Wokwi's simulator runs on metered cloud servers with per-session wall-clock caps ([Wokwi CI](https://docs.wokwi.com/wokwi-ci/getting-started)). Velxio is dual-licensed AGPLv3/commercial ([CNX Software](https://www.cnx-software.com/2026/04/04/velxio-open-source-self-hosted-arduino-raspberry-pi-and-esp32-simulator/)). Zephyr native_sim, with deterministic virtual time decoupled from the host, PTY UART, SocketCAN and I2C/SPI/GPIO/ADC emulators ([native_sim docs](https://docs.zephyrproject.org/latest/boards/native/native_sim/doc/index.html)), is a useful complement for Zephyr products. It cannot replace Renode, because it never runs the real firmware binary. Whether Renode covers AVR or RP2040 was not checked. If either family matters, the MIT JavaScript cores are the cheapest addition.

## ngspice 47 closes the power-stage gaps without a new engine

ngspice is still the right circuit engine, and the most valuable circuit work is upgrading it rather than replacing it. The last three releases add features that map almost one-to-one onto embeddyn's power-electronics gaps. ngspice-47 (Aug 2026) adds a **VDMOS soft-recovery model**. ngspice-46 (Mar 2026) adds a **diode soft-recovery model**, enables CIDER with the KLU solver, and adds voltage-based truncation-error correction. ngspice-45 lets the `d_cosim` code model run **VHDL through GHDL**. ngspice-44 added Icarus Verilog to `d_cosim`, plus shared-library API functions for reset and for skipping `.spiceinit` ([ngspice news](https://ngspice.sourceforge.io/news.html)). Dead-time ringing, reverse recovery and the H-bridge's diode behaviour now have device models. A dead-time generator or protection latch written in Verilog or VHDL can run inside the same libngspice transient that embeddyn already advances 1 ms at a time, with no second synchronization loop. The new reset API also helps embeddyn re-run scenarios inside one process. The `d_cosim` timing details could not be retrieved because the ngspice digital page returned 404, so a local spike should confirm how it behaves under stop/resume stepping.

Xyce 7.10 (Aug 2025) is mature and parallel ([Xyce news](https://xyce.sandia.gov/news/)). Its coupling interfaces, though, are a C++ GenExt API and a ctypes MixedSignal interface that were documented on Python 2.x and called "still under development" ([OSTI 1762646](https://www.osti.gov/servlets/purl/1762646)). That makes Xyce a cross-check engine, not a co-simulation target. The Python wrappers add nothing to the stepping loop. spicelib (GPL-3.0) is batch and raw-file oriented and drives LTspice, QSPICE, ngspice and Xyce ([spicelib](https://pypi.org/project/spicelib)). It is useful for golden-reference sweeps against the free but closed LTspice and QSPICE engines. PySpice's last release is 1.5 and appears stale ([PySpice](https://pypi.org/project/PySpice)), and its fork InSpice requires Python ≥3.12 ([InSpice](https://pypi.org/project/InSpice/)).

There is no open PLECS equivalent with a Python stepping API, so power electronics needs a two-tier design. Long system runs use an averaged H-bridge or inverter (duty-cycle input, power balance), and short detailed windows use the existing switched ngspice model. Averaged Modelica converter models are "very fast to simulate, as no switching events are needed" ([SAE 2016-01-2029](https://sae.org/publications/technical-papers/content/2016-01-2029/?PC=DL2BUY)). For motor drives, **motulator** (MIT, pure Python, induction/SynRM/PMSM plants built from motor, mechanics and converter submodels, v0.7.3 ([PyPI](https://pypi.org/project/motulator/))) is the lowest-friction plant or reference. GeckoCIRCUITS is GPL, Java-based and of uncertain activity ([GeckoCIRCUITS](https://github.com/geckocircuits)). Julia's MTK electrical library has only basic NMOS/PMOS/diode devices ([MTKStdLib](https://docs.sciml.ai/ModelingToolkitStandardLibrary/stable/API/electrical)). Neither is worth a second runtime.

For thermal modelling, the vendor models already provide a hook. Infineon Level 3 models are electro-thermal ([Infineon AN](https://www.infineon.com/dgdl/Infineon-ApplicationNote_PowerMOSFET_SimulationModels-AN-v01_00-EN.pdf)), Rohm L2 adds an RC self-heating network ([Rohm](https://www.rohm.com/support/design-model)), and Nexperia exposes a Tmb pin for a PCB or heatsink model ([Nexperia IAN50012](https://nexperia.com/applications/interactive-app-notes/IAN50012_Nexperia_Precision_Electrothermal_models_for_Power_MOSFETs)). Driving those pins from an embeddyn-side Foster/Cauer network, updated every step from ngspice losses, is numerically benign: thermal time constants run from milliseconds to seconds. Custom compact models, such as SiC MOSFETs or a Verilog-A gate driver, go through OpenVAF-reloaded (GPLv3 compiler, used offline) to `.osdi` files loaded by ngspice ([ngspice OSDI](https://ngspice.sourceforge.io/osdi.html)). Whether Infineon Level 3 models run unmodified in ngspice was not confirmed. Each vendor library needs a smoke test, and each vendor's redistribution terms need checking before bundling.

The KiCad round trip should stay file-based. The KiCad 9/10 IPC API talks only to a running GUI, has no export, and has no schematic commands yet. Export is deferred to KiCad 11 ([KiCad IPC dev-docs](https://dev-docs.kicad.org/en/apis-and-binding/ipc-api/for-addon-developers/)). The robust path is to annotate symbols with `Sim.Device/Type/Pins/Params` ([KiCad sim_model.h](https://docs.kicad.org/doxygen/sim__model_8h_source.html)), run `kicad-cli sch export netlist --format spice` ([kicad-cli source](https://docs.kicad.org/doxygen/command__sch__export__netlist_8cpp_source.html)), load the result into libngspice, and use the reference designator plus the symbol UUID from `.kicad_sch` as the stable ID. A May 2025 bug in which a netlist simulated in KiCad but failed in standalone ngspice ([ngspice bug 791](https://sourceforge.net/p/ngspice/bugs/791)) is a reason to add regression tests to this pipeline. For the browser Lab GUI, the MIT **wokwi-elements** web components ([wokwi-elements](https://www.github.com/wokwi/wokwi-elements)) provide part visuals without simulation behaviour. Fritzing part art is CC BY-SA ([openSUSE fritzing-parts](https://build.opensuse.org/package/show/openSUSE/fritzing-parts?rev=1)), so it carries share-alike obligations.

## MuJoCo should replace the Webots bridge as the mechanical default

The Webots bridge does not simulate any mechanics. The controller in `examples/mechatronics/controllers/embeddyn_bridge/embeddyn_bridge.py` integrates its own explicit-Euler single-inertia ODE. It calls `robot.step(max(1, round(dt*1000)))` only to advance the clock, so a 0.1 ms macro step silently becomes a 1 ms Webots step and time drifts. Its adapter also claims `mechanical_contacts: True`, which nothing exercises (from local code inspection). Webots cannot fix the granularity on its own: `robot.step()` takes integer milliseconds, and Webots has no in-memory state snapshot. With `synchronization TRUE` it does give clean lock-step at ms granularity ([Webots robot reference](https://github.com/omichel/webots-doc/blob/master/reference/robot.md)). If Webots stays, it should become an `<extern>` controller that drives real `Motor`/`PositionSensor` devices, asserts integer-ms steps instead of rounding, and is demoted to an optional scene backend.

**MuJoCo is the best first integration.** It runs in-process from Python, `mj_step` is fixed-step, and full-state save/restore is native through `mj_getState`/`mj_setState` ([MuJoCo API](https://mujoco.readthedocs.io/en/3.6.0/APIreference/APIfunctions.html)), with `mj_extractState` added in 3.5.0 ([3.8.0 API](https://mujoco.readthedocs.io/en/3.8.0/APIreference/APIfunctions.html)). So it satisfies embeddyn's `SimulatorAdapter.checkpoint/restore` contract that Webots cannot. Since 3.7.0 it has a `dcmotor` actuator with inductance, cogging, LuGre friction and thermal resistance drift ([changelog 3.7.0](https://mujoco.readthedocs.io/en/3.7.0/changelog.html)). Its technical note documents gear-reflected inertia, gearbox efficiency, and **backlash through a dual-joint decomposition** ([dcmotor note](https://mujoco.readthedocs.io/en/latest/_static/dcmotor.pdf)), which covers the motor, gearbox and RC-servo cases. MuJoCo 4.0.0 shipped on 2026-11-06 and 4.0.1 on 2026-11-11 ([MuJoCo changelog](https://mujoco.readthedocs.io/en/latest/changelog.html)). The 4.0 line has three caveats. It **drops Python 3.10**. It splits the package into `mujoco-core`, `mujoco-studio` and `mujoco`. And force-saturated actuators no longer contribute implicit derivatives, which can move regression baselines (same source). There is also a modelling trap: when ngspice already owns winding current and back-EMF, MuJoCo should use plain `motor` actuators with `gear`. Using `dcmotor` there would double-count the electrical dynamics. `dcmotor` belongs only in mechanics-only runs. The bit-reproducibility of `mj_step` on the same build and CPU is the researchers' prior knowledge, not something re-checked here. A CI test that checkpoints, runs, restores, re-runs and compares bitwise should be the first acceptance gate.

Project Chrono is the stronger second engine where explicit mechanism elements and FMI matter. Chrono 9.0 added **FMI 2.0 co-simulation FMU export and import** ([Chrono 9.0](https://groups.google.com/g/projectchrono/c/Zz7n22fSJh8/m/6mjqxSefBQAJ)), though only as co-simulation FMUs ([Chrono::FMI](https://api.projectchrono.org/module_fmi_installation.html)). Chrono 10.0 (Mar 2026) added checkpointing for Chrono and Chrono::Vehicle ([Chrono 10.0](https://groups.google.com/g/projectchrono/c/OGb3bWbCjbc)). PyChrono still ships only through conda, which is friction for a pip-based project. Drake has excellent contact, monthly releases and the MeshCat browser viewer, but it has no FMI support in any release notes searched ([Drake release notes](https://drake.mit.edu/release_notes/v1.55.0.html)) and a heavier learning curve. PyBullet's last official release was 3.2.7 in January 2025, and Snyk rates it inactive ([Snyk](https://snyk.io/advisor/python/pybullet)). Newton, Genesis and Isaac Sim are GPU-first and batch-oriented, and Isaac's determinism is conditional ([NVIDIA FAQ](https://perspectives.nvidia.com/isaac-sim/task/faq/deterministic-replay-mechanisms-reproducible-benchmarks-1/)). All three are a poor fit for a single scene stepped at 1 ms. Gazebo Jetty now has a headless server package and Python stepping through `TestFixture` ([gz-sim Python](https://gazebosim.org/api/sim/9/python_interfaces.html)), but it runs as a separate process behind a transport and has no snapshot API, so it suits ROS-world scenes best.

For high-fidelity 1-D drivetrains, OpenModelica-exported FMUs built from MSL Rotational elements (gears, elasto-backlash, bearing friction) run through embeddyn's existing `fmu.py` adapter with no new runtime code. The 3-D view should be decoupled from physics. The orchestrator streams decimated body poses, and the Lab GUI loads URDF or MJCF meshes once with three.js and NASA JPL's `urdf-loaders` ([JPL URDF loaders](https://discourse.openrobotics.org/t/web-based-urdf-visualization-tool-and-library-opensourced-from-nasa-jpl/14404)) or `mujoco_wasm`. Rerun's URDF loader and the community `rerun-loader-mjcf` cover recorded replays ([Rerun URDF](https://rerun.io/docs/howto/urdf); [rerun-loader-mjcf](https://pypi.org/project/rerun-loader-mjcf/0.4.0/)). For CAD, onshape-to-robot emits MJCF directly ([onshape-to-robot](https://onshape-to-robot.readthedocs.io/en/latest/)). The Foxglove 2.0 app went closed-source ([ROS Discourse](https://discourse.openrobotics.org/t/foxglove-2-0-integrated-ui-new-pricing-and-open-source-changes/36583)), so new work should not depend on it.

## FMI should be the interchange spine, with Modelica kept offline

embeddyn's own ctypes FMI 2/3 importer is an asset. It needs validation, state handling and an export path, not a replacement. **FMPy** (BSD-2, v0.3.32, Sep 2026) supports FMI 1/2/3 CS and ME, contains a `validation` module and an SSP reader and simulator, and wraps `fmi3GetFMUState`, clocks and `fmi3UpdateDiscreteStates` ([FMPy](https://github.com/CATIA-Systems/FMPy); [fmi3.py](https://github.com/CATIA-Systems/FMPy/blob/main/src/fmpy/fmi3.py)). It is the obvious test-time oracle: it can validate every imported or exported `modelDescription.xml` and cross-check trajectories. The **Reference-FMUs** (BSD-2, v0.0.42, Oct 2026) provide redistributable conformance targets, in FMI 2 and FMI 3 variants, for state events (BouncingBall), time events (Stair), a DAE (Roberts), arrays and structural parameters (StateSpace) ([Reference-FMUs](https://github.com/modelica/Reference-FMUs)). Checkpointing FMUs then means calling `fmi2GetFMUstate`/`SerializeFMUstate` and their FMI 3 equivalents, gated on the capability flags. libcosim's CBOR state serialization, added in v0.11.0, is a design precedent ([libcosim CHANGELOG](https://github.com/open-simulation-platform/libcosim/blob/master/CHANGELOG.md)).

For export, **PythonFMU3** (MIT, v1.3.0, released 2026-11-18) turns a Python class into an FMI 3.0 FMU supporting both **co-simulation and model exchange, with events, arrays, units and FMU state** ([PythonFMU3](https://github.com/StephenSmith25/PythonFMU3)). PythonFMU (MIT, v0.7.0) is the FMI 2.0 CS fallback for older importers ([PythonFMU](https://github.com/NTNU-IHB/PythonFMU)). Both have two weaknesses. They produce tool-coupling FMUs that need Python and embeddyn on the target, and PythonFMU3 has a single maintainer with 14 stars. A standalone FMU would need generated C code against the BSD-2 FMI headers, which is a much larger project. UniFMU (v1.1.0) adds remote FMUs over ZeroMQ, but its INTO-CPS licence is GPL-3-based ([UniFMU LICENSE](https://github.com/INTO-CPS-Association/unifmu/blob/master/LICENSE.txt)), so it is a source of ideas rather than a dependency.

Acausal physics is best handled by Modelica. OpenModelica exports FMI 2.0 ME and CS FMUs with CVODE embedded in CS FMUs, while its FMI 3.0 export remains "experimental" ([OM FMI chapter](https://openmodelica.org/doc/OpenModelicaUsersGuide/latest/fmitlm.html)). The MSL is BSD-3 and active ([MSL](https://github.com/modelica/ModelicaStandardLibrary)). An offline build script that turns MSL machines, rotational drivetrains and thermal networks into FMI 2.0 CS FMUs therefore gives embeddyn stiff multi-domain plants with no new runtime dependency. OMSimulator 3.x is the strongest open SSP tool: a pip package with SSP/SSV import and export, FMUs from other vendors, and mixed FMI2/FMI3 connections ([OM Workshop 2026](https://openmodelica.org/images/M_images/OpenModelicaWorkshop_2026/Lennart_Arun_OMSimulator_talk_OM_2026.pdf)). It carries the OSMC Public License, however ([OMSimulator](https://github.com/OpenModelica/OMSimulator)), and the OMPython licence claims conflict between sources. SSP 2.0 (Dec 2024) is current and adds FMI 3.0 vECU interconnection ([SSP 2.0](https://ssp-standard.org/news/2024-12-20-ssp-2-0-release/)). An SSP file is a zip containing `SystemStructure.ssd` XML, so embeddyn should write its own minimal SSD/SSV reader and writer and use OMSimulator and FMPy only as optional cross-validation oracles.

Two more gaps have no off-the-shelf answer. None of the masters surveyed documents a general algebraic-loop solver. The native route is to detect direct-feedthrough cycles from FMI `<ModelStructure>`, then iterate with GetFMUState rollback. For distributed co-simulation, libcosim (MPL-2.0, v0.11.2) offers proxyfmu and a DCP proof of concept but documents FMI 1/2 only ([libcosim docs](https://open-simulation-platform.github.io/libcosim/distributed)). DCPLib has made no release since v0.2 in 2021 ([DCPLib](https://github.com/modelica/DCPLib)). Ecos (MIT, `ecospy`, SSP 1.0, partial FMI 3) is a permissive alternative master with a small community ([Ecos](https://github.com/Ecos-platform/ecos)). Julia offers export only through FMIExport.jl, which brings a second runtime, and Dyad's FMU generation is tied to JuliaHub ([Dyad FMU docs](https://help.juliahub.com/dyad/v0.5/analyses/fmugeneration.html)). DCP and Julia should both be deferred.

## Bus, ROS and HIL bridges must keep determinism inside a boundary

Every real-time integration needs the same rule. Observing the lock-step from outside is safe. Injecting into it happens at sync points, is non-deterministic, and must be logged for replay. Renode's SocketCAN bridge forwards Classical CAN and CAN-FD to `vcan0` or real adapters on Linux. It drops CAN XL, and its documentation says nothing about timing ([Renode CAN docs](https://renode.readthedocs.io/en/latest/host-integration/can.html)). Antmicro's August 2026 demo ran Toyota's RAMN board in Renode with CARLA, and the virtual board was usable as a USB-CAN device with standard Linux tools ([Antmicro RAMN + CARLA](https://antmicro.com/blog/2026/08/toyota-ramn-and-carla-in-renode)). That is a direct precedent for embeddyn's emulated-ECU-plus-physics use case. The right design is an embeddyn CAN domain that owns a frame queue stamped with virtual time. It connects Renode `canHub`s inside the lock-step through the External Control CAN API and mirrors traffic out with python-can (4.6.1 ([pepy](https://pepy.tech/project/python-can))). cantools, canopen and udsoncan sit on top of that to turn DBC signals into Lab GUI plot channels. Their licences (cantools and canopen MIT, python-can LGPL-3.0) come from background knowledge and should be confirmed. CAN tests on CI runners should use Renode-internal hubs or python-can's `virtual` interface, because `vcan` kernel modules may not be loadable there.

For robotics middleware, ROS 2 Kilted made Zenoh a Tier-1 middleware ([Kilted announcement](https://discourse.ros.org/t/ros-2-kilted-kaiju-release/43902)). An embeddyn gateway written with zenoh-python or rclpy can publish signals and drive `/clock` from simulation time, so ROS nodes with `use_sim_time` run in lock-step without a hard ROS dependency. micro-ROS-on-Zephyr firmware has run in Renode ([Zephyr blog](https://zephyrproject.org/test-driven-development-of-multi-node-zephyr-micro-ros-solutions-with-renode/)), but the module was tested on Zephyr 2.7/3.1 ([micro_ros_zephyr_module](https://www.github.com/micro-ROS/micro_ros_zephyr_module)), so expect porting work. For HIL, labgrid (pytest-native, v25.0 May 2025 ([labgrid docs](https://labgrid.readthedocs.io/en/v25.0/index.html))) handles power, serial and board reservation. pyOCD 0.44 ([pyOCD](https://pyocd.io/posts/2026/04-01-pyocd-0.44.0-released.html)) and probe-rs 0.31 ([probe-rs](https://github.com/probe-rs/probe-rs/releases/tag/v0.31.0)) flash the same ELF that runs in Renode. A "hardware proxy" domain implementing the same `step(dt)` interface lets a real board replace an emulated one. When that happens the master clock must switch to wall-clock pacing, which Renode does by default unless `AdvanceImmediately` is set ([Renode time framework](https://renode.readthedocs.io/en/latest/advanced/time_framework.html)), and watchdogs and actuator limits must be armed. libsigrok has shown no upstream release since 0.5.2 ([Debian](https://tracker.debian.org/pkg/libsigrok)), so it is capture-only at best.

For telemetry, one MCAP file per run with channels stamped in simulation time is the right default. Rerun reads MCAP natively since 0.30 ([Rerun 0.30](https://sourceforge.net/projects/rerun.mirror/files/0.30.0)) and puts signals and 3-D on one timeline. Parquet export serves pandas/polars analysis. InfluxDB 3 Core (MIT/Apache, GA April 2025, five-database limit, no compactor ([InfluxData](https://www.influxdata.com/blog/influxdb-3-oss-ga))) plus Grafana fits only a long-running live-twin deployment. For digital twins, MQTT (paho) is the cheapest live link and OPC UA (asyncua) exposes the simulation to SCADA tools. The BaSyx Python SDK 2.x (AAS metamodel v3.1 ([BaSyx 2.1.0](https://projects.eclipse.org/node/35987))) handles model metadata rather than real-time data. Eclipse Ditto is a heavyweight JVM fleet service, and its Python client is at 0.3.0 with no GitHub releases ([ditto-client](https://pypi.org/project/ditto-client/)), so it does not fit a desktop co-simulation tool. For CI, one pinned image built on `antmicro/renode` ([Docker Hub](https://hub.docker.com/r/antmicro/renode)) plus `libngspice0` and the Python venv, with `antmicro/renode-test-action@v5` for Robot suites ([Antmicro blog](https://antmicro.com/blog/2024/10/renode-github-action-for-automated-testing-in-simulation)), covers the core. Webots, if kept, gets its own optional image, because `cyberbotics/webots` is GPU-oriented and its newest tag is `R2025a-ubuntu22.04` ([Docker Hub](https://hub.docker.com/r/cyberbotics/webots/tags)).

## Forge plugins turn integrations into versioned capabilities

The Forge merge gives each integration a natural home and a licensing firewall. Forge's Python plugin hosts run out of process and talk JSON-RPC to a Rust registry with versioned capabilities. GPL and OSMC-PL tools (GHDL, Icarus, simavr, QEMU, spicelib, OpenVAF, OMSimulator) can therefore live in separately distributed plugins that exchange data at arm's length. The permissive core (Renode, MuJoCo, FMPy, PythonFMU3, python-can, MCAP) can sit in embeddyn proper. Whether a JSON-RPC boundary satisfies a given licence is a legal question, not an engineering one, and should be reviewed before shipping.

The existing plugins connect directly. **Pin Configurator** should emit a pin-plan capability that embeddyn compiles into Renode `.repl` connections and External Control bindings: GPIO, ADC and PWM signal maps, CAN hub membership, which I2C address gets which sensor model, and which timer gets the encoder peripheral. The same plan can also generate KiCad `Sim.Pins` fields, so firmware pins, schematic nets and simulation signals share one source of truth. **OpenHDL Designer** has two consumers. Bus-attached Verilog compiles through Verilator into a `libV` Renode peripheral on APB3, AXI4 or Wishbone. Gate-driver and dead-time logic goes into ngspice `d_cosim` with Icarus or Verilator. A cocotb capability can run OpenHDL testbenches in CI. **Route Core**'s exact scope was not in the research notes. If it owns PCB or net routing, it should consume the kicad-cli netlist keyed by reference designator and symbol UUID, and it is the eventual home for the KiCad IPC features (live highlighting, back-annotation) once schematic commands land. New plugins would follow the domain split: an FMU Exchange plugin (FMPy validation, PythonFMU3 export, SSP read/write), a Mechanics plugin (MuJoCo adapter plus a three.js viewer panel), a Bus plugin (python-can/cantools with DBC-driven signal panels), a Telemetry plugin (MCAP writer and Rerun launch), and a HIL plugin. probe-rs is a Rust crate, so the HIL plugin could fit the Rust registry side natively.

## Conclusion

The research changes the question. embeddyn does not mainly need more engines. It needs **checkpointable, deterministic adapters**, and that one property sorts the candidates better than licence or popularity. Renode, MuJoCo, FMI state functions and libngspice's new reset API all support save, restore and exact re-run. Webots, Gazebo, QEMU without icount and every cloud or GPU engine do not. Rollback-based algebraic-loop solving, what-if tuning and bitwise-reproducible tolerance sweeps all depend on that property, so the first concrete deliverable should be a single cross-domain checkpoint/restore test spanning Renode, ngspice, MuJoCo and an FMU. Shipping that test before any new feature puts embeddyn's tuning and estimation story on solid ground.

The Forge merge resolves a strategic tension the notes hint at. The best acausal, mixed-signal and validation tools (OpenModelica, OMSimulator, GHDL, Icarus, spicelib, OpenVAF) are copyleft or OSMC-licensed, while embeddyn's runtime should stay permissive. Forge's process-isolated, capability-versioned plugins let those tools be first-class without entering the core. Several facts remain unverified and are the right first spikes: Renode's exact licence, MuJoCo's cross-run bit-exactness, whether OpenModelica- and Chrono-exported FMUs actually set `canGetAndSetFMUstate`, `d_cosim` behaviour under stop/resume stepping, and per-step overhead with Renode in the loop at 0.1 ms.
